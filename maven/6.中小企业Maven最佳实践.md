# 中小企业，Maven最佳实践

## 先说结论

对于已经拥有 Nexus、Artifactory 等私有仓库的中小企业，推荐的架构不是让每台开发机分别判断“公共依赖走阿里云，私有依赖走公司仓库”，而是：

```text
开发机 / CI
      |
      | 只访问一个地址
      v
公司 Nexus 的 maven-public Group
      |-- company-releases：公司正式版本
      |-- company-snapshots：公司快照版本
      `-- maven-proxy：代理阿里云或 Maven Central
```

开发机只配置公司 Nexus：

```xml
<mirrorOf>*</mirrorOf>
```

由 Nexus 统一完成私有包存储、公共包代理、缓存、权限和审计。这是配置最简单、构建最稳定、也最容易管理的方案。

如果企业暂时无法让 Nexus 代理阿里云，也可以使用过渡方案：Maven Central 请求走阿里云，其他仓库请求走公司 Nexus。但这种方案需要更仔细地配置 `mirrorOf`，长期维护成本也更高。

## Maven并不知道一个依赖是公共包还是私有包

假设项目声明了下面的依赖：

```xml
<dependency>
    <groupId>com.example.company</groupId>
    <artifactId>order-sdk</artifactId>
    <version>1.2.0</version>
</dependency>
```

Maven 不会根据 `com.example.company` 自动判断这是公司私有包。它只会把依赖坐标转换成仓库路径：

```text
com/example/company/order-sdk/1.2.0/order-sdk-1.2.0.jar
```

然后按照当前生效的仓库列表逐个查找：

```text
本地仓库 → 第一个远程仓库 → 第二个远程仓库 → ……
```

在哪个仓库先找到，就从哪个仓库下载。`mirrorOf` 管理的是“仓库请求如何转发”，不是“某个依赖应该去哪里下载”。

## 理解 mirrorOf

可以把 Maven 仓库理解成仓库网点，把 mirror 理解成统一接单的配送中心。

```xml
<mirrorOf>central</mirrorOf>
```

表示只接管 ID 为 `central` 的仓库请求。

```xml
<mirrorOf>*</mirrorOf>
```

表示接管所有仓库请求。

常用表达式如下：

| 配置 | 含义 |
|---|---|
| `central` | 只接管 Maven Central |
| `repo1` | 只接管 ID 为 `repo1` 的仓库 |
| `repo1,repo2` | 接管多个指定仓库 |
| `*` | 接管所有仓库 |
| `*,!repo1` | 接管所有仓库，但排除 `repo1` |
| `external:*` | 接管除 localhost 和本地文件仓库以外的仓库 |
| `external:http:*` | 接管外部 HTTP 仓库，不包含 localhost |

同一个仓库请求最终只会匹配一个镜像。Maven 不会把同一个请求同时发送给多个 `mirrorOf=*`，而是选择一个匹配项。精确的仓库 ID 匹配优先；没有精确匹配时，再按照镜像声明顺序选择第一个通配匹配项。

## 推荐方案：所有下载统一经过公司 Nexus

### Nexus仓库规划

对于大多数中小企业，四个仓库已经足够：

| 仓库名称 | Nexus 类型 | 用途 |
|---|---|---|
| `company-releases` | hosted | 保存公司正式版本 |
| `company-snapshots` | hosted | 保存公司 SNAPSHOT 版本 |
| `maven-proxy` | proxy | 代理阿里云或 Maven Central |
| `maven-public` | group | 聚合前三个仓库，提供统一下载入口 |

建议在 `maven-public` 中将 hosted 仓库放在 proxy 仓库前面：

```text
1. company-releases
2. company-snapshots
3. maven-proxy
```

这样 Nexus 会优先查找企业内部组件，再访问外部代理。

`maven-proxy` 的上游可以根据企业网络实测选择：

- 阿里云 Maven 公共仓库：`https://maven.aliyun.com/repository/public`
- Maven Central：`https://repo.maven.apache.org/maven2`

需要注意：代理服务是否允许被 Nexus 作为上游、重定向是否稳定，应在当前网络环境中实际验证。不要只验证浏览器能打开首页，应使用真实 POM 和 JAR 请求验证。

### 开发机 settings.xml

开发机只连接公司的 `maven-public` Group：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<settings xmlns="http://maven.apache.org/SETTINGS/1.2.0"
          xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
          xsi:schemaLocation="http://maven.apache.org/SETTINGS/1.2.0
                              https://maven.apache.org/xsd/settings-1.2.0.xsd">

    <mirrors>
        <mirror>
            <id>company-nexus</id>
            <name>Company Nexus</name>
            <url>https://nexus.example.com/repository/maven-public/</url>
            <mirrorOf>*</mirrorOf>
        </mirror>
    </mirrors>

    <profiles>
        <profile>
            <id>company-repositories</id>

            <repositories>
                <repository>
                    <id>company-public</id>
                    <url>https://nexus.example.com/repository/maven-public/</url>
                    <releases>
                        <enabled>true</enabled>
                    </releases>
                    <snapshots>
                        <enabled>true</enabled>
                    </snapshots>
                </repository>
            </repositories>

            <pluginRepositories>
                <pluginRepository>
                    <id>company-plugins</id>
                    <url>https://nexus.example.com/repository/maven-public/</url>
                    <releases>
                        <enabled>true</enabled>
                    </releases>
                    <snapshots>
                        <enabled>true</enabled>
                    </snapshots>
                </pluginRepository>
            </pluginRepositories>
        </profile>
    </profiles>

    <activeProfiles>
        <activeProfile>company-repositories</activeProfile>
    </activeProfiles>
</settings>
```

这里的关键点是：

- `mirrorOf=*`：任何下载请求都通过公司 Nexus。
- `repositories`：同时允许 release 和 snapshot 依赖。
- `pluginRepositories`：Maven 插件也从公司 Nexus 下载。
- 项目 POM 不需要重复声明阿里云和公司下载仓库。

### 上传公司依赖

下载和上传是两条不同的链路：

- `mirror`、`repositories`：控制依赖从哪里下载。
- `distributionManagement`：控制公司组件发布到哪里。

项目 POM 可以统一继承下面的发布配置：

```xml
<distributionManagement>
    <repository>
        <id>company-releases</id>
        <name>Company Releases</name>
        <url>https://nexus.example.com/repository/company-releases/</url>
    </repository>

    <snapshotRepository>
        <id>company-snapshots</id>
        <name>Company Snapshots</name>
        <url>https://nexus.example.com/repository/company-snapshots/</url>
    </snapshotRepository>
</distributionManagement>
```

认证信息放在开发机或 CI 的 `settings.xml` 中，不要写进项目 POM：

```xml
<servers>
    <server>
        <id>company-releases</id>
        <username>${env.MAVEN_REPO_USERNAME}</username>
        <password>${env.MAVEN_REPO_PASSWORD}</password>
    </server>

    <server>
        <id>company-snapshots</id>
        <username>${env.MAVEN_REPO_USERNAME}</username>
        <password>${env.MAVEN_REPO_PASSWORD}</password>
    </server>
</servers>
```

`server.id` 必须与 `distributionManagement` 中的仓库 ID 完全一致，否则 Maven 找不到对应凭据。

## 过渡方案：公共包走阿里云，私有包走公司 Nexus

如果暂时不能让 Nexus 代理公共仓库，可以让客户端直接访问两类仓库：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<settings xmlns="http://maven.apache.org/SETTINGS/1.2.0"
          xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
          xsi:schemaLocation="http://maven.apache.org/SETTINGS/1.2.0
                              https://maven.apache.org/xsd/settings-1.2.0.xsd">

    <mirrors>
        <mirror>
            <id>aliyun-central</id>
            <name>Aliyun Maven Mirror</name>
            <url>https://maven.aliyun.com/repository/public</url>
            <mirrorOf>central</mirrorOf>
        </mirror>

        <mirror>
            <id>company-nexus</id>
            <name>Company Nexus</name>
            <url>https://nexus.example.com/repository/maven-public/</url>
            <mirrorOf>*,!central</mirrorOf>
        </mirror>
    </mirrors>

    <profiles>
        <profile>
            <id>company-repositories</id>
            <repositories>
                <repository>
                    <id>company-public</id>
                    <url>https://nexus.example.com/repository/maven-public/</url>
                    <releases>
                        <enabled>true</enabled>
                    </releases>
                    <snapshots>
                        <enabled>true</enabled>
                    </snapshots>
                </repository>
            </repositories>
            <pluginRepositories>
                <pluginRepository>
                    <id>company-plugins</id>
                    <url>https://nexus.example.com/repository/maven-public/</url>
                    <releases>
                        <enabled>true</enabled>
                    </releases>
                    <snapshots>
                        <enabled>true</enabled>
                    </snapshots>
                </pluginRepository>
            </pluginRepositories>
        </profile>
    </profiles>

    <activeProfiles>
        <activeProfile>company-repositories</activeProfile>
    </activeProfiles>
</settings>
```

这套配置的路由是：

```text
central           → 阿里云
company-public    → 公司 Nexus
company-plugins   → 公司 Nexus
其他仓库          → 公司 Nexus
```

它能够工作，但存在明显缺点：

- 公共依赖绕过了公司 Nexus，缓存、审计和访问控制不统一。
- 每台开发机和每个 CI Agent 都需要维护同一份复杂配置。
- 阿里云镜像发生延迟或缺包时，Maven 不会自动把同一个仓库请求切换到第二个镜像。
- 构建结果更容易受到开发机配置差异影响。

因此，它更适合作为过渡方案，不建议作为长期标准。

## 最容易踩的坑

### 同时配置两个 mirrorOf=*

下面的配置有歧义：

```xml
<mirror>
    <id>aliyun</id>
    <mirrorOf>*</mirrorOf>
</mirror>

<mirror>
    <id>company-nexus</id>
    <mirrorOf>*</mirrorOf>
</mirror>
```

Maven 不会先去阿里云，找不到后再去公司 Nexus。对于一个仓库请求，它只会选择一个镜像，通常表现为第一个通配匹配项接管请求。

### mirror不会让一个依赖凭空存在

如果一个公司 JAR 只上传到了私有仓库，那么阿里云和 Maven Central 不会自动拥有它。镜像配置只能改变请求地址，不能把私有包同步到公共仓库。

### SNAPSHOT仓库没有启用

版本带有 `-SNAPSHOT` 时，Maven 只会查询允许 snapshot 的仓库。即使 Nexus 中存在该文件，如果客户端仓库策略禁用了 snapshot，依然可能解析失败。

### 只配置依赖仓库，没有配置插件仓库

依赖和 Maven 插件存在不同的仓库配置入口。只配置 `<repositories>`，可能出现依赖能下载，但 Maven 插件下载失败的情况。

### 把账号密码提交到Git

POM 和共享的 settings 模板中不要保存真实密码。开发机可以使用 Maven 密码加密，CI 优先通过凭据管理系统注入环境变量或临时 settings 文件。

### 正式版本允许重复覆盖

建议正式版本仓库禁止重复发布，相同版本一旦发布就保持不可变；需要修复时发布新版本。SNAPSHOT 可以更新，但 CI 应记录实际解析到的时间戳版本，避免故障时无法复现。

## 如何验证配置是否真的生效

查看 Maven 最终合并后的 settings：

```bash
mvn help:effective-settings
```

查看激活的 profile：

```bash
mvn help:active-profiles
```

单独验证一个依赖：

```bash
mvn dependency:get \
  -Dartifact=com.example.company:order-sdk:1.2.0 \
  -Dtransitive=false
```

临时指定 settings，避免直接修改全局配置：

```bash
mvn -s ./settings-company.xml clean package -DskipTests
```

调试时重点观察日志中的仓库名称：

```text
Downloading from aliyun-central: ...
Downloading from company-nexus: ...
```

不要只看本地 `~/.m2/repository` 中有没有 JAR。本地缓存可能来自旧仓库，Maven 还会通过 `_remote.repositories` 等文件记录它的来源。最可靠的验证方式是使用一个新的临时本地仓库：

```bash
mvn -s ./settings-company.xml \
  -Dmaven.repo.local=/tmp/maven-repo-validation \
  dependency:get \
  -Dartifact=com.example.company:order-sdk:1.2.0 \
  -Dtransitive=false
```

## 中小企业落地检查清单

- [ ] 使用 Nexus 或 Artifactory 管理公司 Maven 组件。
- [ ] 分开管理 release 和 snapshot hosted 仓库。
- [ ] 使用一个 group 仓库作为统一下载入口。
- [ ] group 中将公司 hosted 仓库排在外部 proxy 仓库之前。
- [ ] 开发机和 CI 使用同一份受控 settings 模板。
- [ ] 推荐客户端配置 `mirrorOf=*`，只访问公司 Nexus。
- [ ] Nexus 再代理阿里云或 Maven Central，并验证真实 POM/JAR 请求。
- [ ] 同时配置普通依赖仓库和插件仓库。
- [ ] 发布凭据不进入 Git，通过 Maven 加密或 CI Secret 管理。
- [ ] 正式版本禁止覆盖，SNAPSHOT 设置合理的清理策略。
- [ ] 构建固定 Maven、JDK、插件、父 POM 和依赖版本。
- [ ] 定期备份 Nexus Blob、数据库和配置，并实际演练恢复。

## 总结

中小企业 Maven 仓库治理的关键，不是写出更复杂的 `settings.xml`，而是减少开发机需要做的决定。

最推荐的模型是：

```text
开发机和 CI只认公司 Nexus
              ↓
Nexus统一管理私有包、公共代理、缓存、权限和审计
```

如果客户端必须同时访问阿里云和公司 Nexus，应确保阿里云只匹配 `central`，公司 Nexus 匹配 `*,!central`，并显式声明公司仓库。不要同时配置两个 `mirrorOf=*`，更不要期待 Maven 在第一个镜像找不到后自动尝试第二个镜像。
