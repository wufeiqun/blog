软件交付质量的几个原则经验

**变更本身不可避免，真正需要解决的问题是：如何在保证研发效率的同时，尽可能降低变更对业务的影响。**


## 通过技术手段提高团队的下限

生产环境出问题最多的是， 技术人员不知道这么做有风险和知道但是没注意。所以保证软件质量最有效的手段是通过技术手段提高团队的下限，减少低级错误。让平台自动拦截已知的、重复发生的、可被规则识别的风险。

#### 代码变更

通过 CI/CD 流水线设置必要的质量门禁。

| 检查项 | 解决的问题 | 技术手段 |
|---|---|---|
| 代码编译 | 避免无法编译的代码进入生产 | Maven、npm |
| 自动化测试 | 减少功能缺陷 | JUnit、Jest |
| 代码质量检查 | 发现潜在 Bug 和代码问题 | SonarQube |
| 安全漏洞扫描 | 发现依赖漏洞和代码安全问题 | SCA、SAST |
| 构建产物管理 | 保证测试和生产使用相同的构建产物 | 制品仓库 |
| 部署后验证 | 判断新版本是否正常运行 | 健康检查、Smoke Test |

例如：

- SonarQube 检测到严重 Bug，阻止发布。
- 自动化测试未通过，阻止发布。
- 部署完成后健康检查失败，阻止继续发布。

需要注意，自动化检测不能保证代码没有问题，但可以拦截一部分常见且可检测的错误。

#### 数据库变更

数据库变更通常比代码发布更加敏感，因为数据修改未必容易回滚。

可以通过 Archery 等 SQL 审核平台设置规则。

| 检查项 | 解决的问题 |
|---|---|
| UPDATE、DELETE 缺少 WHERE | 防止误操作影响整张表 |
| 大表结构变更 | 防止长时间锁表、阻塞业务 |
| SQL 执行计划检查 | 发现潜在性能问题 |
| DDL 规范检查 | 避免不合理的表结构设计 |
| 高风险 SQL 拦截 | 避免误执行 DROP、TRUNCATE 等操作 |
| 权限控制 | 避免开发人员直接使用高权限账户操作生产 |

这里有一个重要原则：

**风险应该尽可能在变更执行前被发现，而不是等事故发生后才依赖人来处理。**

#### 配置和基础设施变更

同样可以增加自动化检查：

- Nginx 配置修改前执行 `nginx -t`。
- Kubernetes YAML 变更前执行 Schema 校验。
- Terraform 变更前执行 `terraform plan`。
- 对生产环境的高风险操作增加权限约束。
- 对关键配置建立版本管理和变更记录。

**最终目标：让平台自动拦截已知的、重复发生的、可被规则识别的风险。**

## 风险分级：不同风险的变更采用不同管理方式

这是整个方案中非常重要的一环。

如果所有生产环境变更都采用同样严格的管理方式，必然带来两个问题：

一是研发效率下降。

二是审批逐渐流于形式。

例如：

一个 FDE 开发的内部轻量级服务，与一个承载核心业务的数据库结构变更，两者的风险显然不同。

如果全部要求晚上发布、经过多级审批，实际上是不合理的。

因此，**应该根据变更风险制定不同的发布策略，而不是对所有变更一刀切。**

风险分级的本质，是把有限的管理资源集中投入到高风险变更上。

可以给服务分级， 也可以默认走流程， 然后通过白名单的方式放行不必审批的应用。

## 变更时间窗口

生产环境变更不一定都必须安排在晚上。

更合理的做法是：

**根据业务流量、影响范围和故障处置能力，选择适当的发布时间。**

例如：

- 高风险、可能中断业务的变更，选择业务低峰期。
- 低风险、具备灰度和回滚能力的变更，可以允许工作时间发布。
- 需要多团队协作的复杂变更，应选择人员齐备、便于处置的时间窗口。

尤其需要注意，晚上发布虽然可能降低用户影响，但也可能面临人员不足、响应速度下降等问题。

因此，晚上发布不应该成为所有生产变更的默认要求。


## 其它

这里还有一个值得强调的观点：

**不要让审批承担所有的风险控制责任。**

一个成熟的变更管理体系，应该逐步从依赖人工审批，发展为依赖自动化质量门禁、标准化发布流程和可观测性。

人工审批主要用于处理平台无法自动判断的业务风险与复杂变更。


### 3. 稳定性与研发效率并不必然冲突

好的变更管理应该做到：

- 对低风险、标准化、可自动验证的变更，尽可能减少人为干预。
- 对高风险、影响范围大、难以恢复的变更，投入更多检查和审批。
- 对所有变更，确保能够及时发现异常并尽可能快速恢复。

从长期来看，应该逐步扩大可以通过自动化完成的低风险变更范围，而不是不断增加审批环节。
