# 为什么 Maven 通常没有 Lock 文件？前端生产 CI 构建最佳实践

在 Java 项目中，我们通常只提交 `pom.xml`；在前端项目中，除了 `package.json`，还必须提交 `package-lock.json`、`pnpm-lock.yaml` 或 `yarn.lock`。

这并不意味着 Maven 天生不需要依赖锁定。更准确的说法是：**Maven 和前端包管理器采用了不同的依赖声明与解析习惯，因此锁定构建结果的方式不同。**

## 一、为什么前端项目需要 Lock 文件？

### 1. `package.json` 往往只声明版本范围

前端依赖经常使用 SemVer 范围：

```json
{
  "dependencies": {
    "vue": "^3.5.0"
  }
}
```

`^3.5.0` 并不是一个唯一版本，它允许安装兼容范围内的后续版本。同一份 `package.json` 在不同时间重新解析，可能得到不同结果。

### 2. 间接依赖数量多，完整依赖树也需要固定

项目直接依赖 A，A 又依赖 B、C，B 和 C 继续依赖其他包。即使直接依赖没有改变，间接依赖的解析结果仍可能发生变化。

Lock 文件会记录：

- 实际安装的精确版本；
- 完整的依赖解析关系；
- 包的下载位置或解析信息；
- 完整性校验值；
- 部分包管理器需要的 peer dependency、workspace 等信息。

因此，`package.json` 更像“允许安装什么”，Lock 文件则回答“这次确定安装什么”。

### 3. Lock 文件是可重复构建的重要输入

团队成员、本地环境和 CI 使用同一份 Lock 文件，可以尽量获得一致的依赖树。Lock 文件应提交到 Git，并在代码评审时和 `package.json` 一起检查。

## 二、为什么 Maven 项目通常没有 Lock 文件？

### 1. Maven 通常直接声明精确版本

Maven 依赖通常写成：

```xml
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-core</artifactId>
    <version>6.2.10</version>
</dependency>
```

这里的 `6.2.10` 是精确版本，而不是一个默认浮动的兼容范围。Maven 也支持版本区间，但生产项目通常不应使用。

### 2. 发布物通过稳定坐标定位

Maven 依赖由以下坐标定位：

```text
groupId + artifactId + version + packaging + classifier
```

正式 Release 版本发布后，仓库通常将其视为不可变制品。只要 POM、仓库和坐标保持不变，依赖解析通常比较稳定。

### 3. Maven 用 BOM 和 `dependencyManagement` 统一版本

企业 Java 项目常通过 Parent POM、BOM 和 `dependencyManagement` 集中管理版本：

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-dependencies</artifactId>
            <version>3.5.4</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

当多个传递依赖带来不同版本时，Maven 会按照依赖调解规则选择版本；项目也可以用 `dependencyManagement` 显式控制最终版本。

### 4. `pom.xml` 既是声明，也是主要版本约束来源

前端通常是“宽松版本范围 + Lock 文件”；Maven 更常见的是“精确版本 + BOM/Parent POM + 依赖调解”。因此，Maven 生态没有形成所有项目都提交统一 Lock 文件的惯例。

## 三、Maven 真的不需要锁定吗？

不是。没有 Lock 文件，不等于构建一定可重复。以下情况仍可能造成漂移：

- 使用 `SNAPSHOT`；
- 使用版本区间、`LATEST` 或 `RELEASE` 等动态版本；
- 没有固定 Maven 插件版本；
- JDK、Maven 或操作系统版本不同；
- 私服覆盖了同坐标制品，破坏 Release 不可变原则；
- 构建产物包含当前时间、文件顺序或环境相关内容。

生产 Maven 构建建议：

1. 提交 Maven Wrapper，并在 CI 使用 `./mvnw`；
2. 固定 JDK 版本和基础镜像的不可变摘要；
3. 依赖与插件使用精确版本，禁止版本区间；
4. 正式发布链路禁止 `SNAPSHOT`；
5. 用 BOM、`dependencyManagement` 和 Maven Enforcer 管理依赖收敛；
6. 配置 `project.build.outputTimestamp`，并使用支持可重复构建的插件版本；
7. 私服中的 Release 制品禁止覆盖。

所以，准确结论是：

> Maven 并非不需要依赖锁定，而是通常依靠精确版本、BOM、构建工具版本和仓库不可变性完成约束；前端则主要依靠 Lock 文件固定完整解析结果。

## 四、前端生产 CI 构建的通用原则

无论使用 npm、pnpm 还是 Yarn，生产 CI 都建议遵循以下原则。

### 1. 仓库中只保留一种 Lock 文件

不要同时提交：

```text
package-lock.json
pnpm-lock.yaml
yarn.lock
```

选择一种包管理器，并删除其他包管理器生成的 Lock 文件，避免本地与 CI 使用不同的依赖树。

### 2. 固定 Node.js 和包管理器版本

建议在 `package.json` 中声明：

```json
{
  "packageManager": "pnpm@10.15.0",
  "engines": {
    "node": "22.x"
  }
}
```

同时使用 `.nvmrc`、`.node-version`、Volta、Corepack 或固定摘要的容器镜像约束运行环境。仅写 `node:22` 仍可能随镜像更新而变化；要求更严格时，应固定具体版本或镜像 digest。

### 3. CI 必须使用冻结安装

CI 不应自动修复或更新 Lock 文件。Lock 文件与 `package.json` 不一致时，应直接失败，让开发者在本地更新后重新提交。

| 包管理器 | CI 推荐命令 | Lock 文件 |
| --- | --- | --- |
| npm | `npm ci` | `package-lock.json` |
| pnpm | `pnpm install --frozen-lockfile` | `pnpm-lock.yaml` |
| Yarn 1 | `yarn install --frozen-lockfile` | `yarn.lock` |
| Yarn 2+ | `yarn install --immutable` | `yarn.lock` |

补充说明：pnpm 和现代 Yarn 在识别到 CI 环境时通常默认启用冻结行为，但在流水线中显式写出参数更清楚，也不依赖环境识别。

### 4. 缓存下载内容，不把旧依赖目录当成构建输入

优先缓存包管理器的下载缓存或内容寻址存储：

- npm：npm cache；
- pnpm：pnpm store；
- Yarn：Yarn cache。

缓存键至少应包含：操作系统、CPU 架构、Node.js 版本、包管理器版本和 Lock 文件摘要。

通常不要跨构建直接复用整个 `node_modules`。其中可能包含软链接、原生模块和安装脚本产物，容易受到运行环境影响。

### 5. 安装、检查、测试和构建分阶段执行

一条清晰的生产流水线通常是：

```text
检出代码
  → 固定工具链
  → 冻结安装
  → lint / typecheck
  → test
  → build
  → 制品校验
  → 发布同一份制品
```

不要在部署环境重新执行一次依赖解析和构建。推荐在 CI 生成一次不可变制品，测试通过后将同一份制品逐级部署。

### 6. 不要关闭 Lock 文件和完整性校验

生产 CI 中不要使用以下思路掩盖问题：

```bash
npm install
pnpm install --no-lockfile
yarn install --no-lockfile
```

也不要在 Lock 文件冲突时直接删除 Lock 文件后重装。正确做法是在受控开发环境中更新依赖、审查差异、运行测试，再提交新的 Lock 文件。

### 7. 私有仓库凭证只通过 CI Secret 注入

项目级 `.npmrc` 可以引用环境变量：

```ini
//registry.example.com/:_authToken=${NPM_TOKEN}
```

但真实 Token 不得写入仓库、镜像层、构建日志或最终制品。发布包时，如果平台支持 OIDC/Trusted Publishing，应优先使用短期身份，而不是长期 Token。

### 8. 安全扫描不能替代版本锁定

Lock 文件解决的是“安装结果是否一致”，不代表依赖一定安全。生产流程还应结合：

- 依赖漏洞扫描；
- 许可证检查；
- SBOM 生成与归档；
- 依赖升级机器人和人工评审；
- 对第三方 PR 中安装脚本、缓存内容和 Lock 文件变更进行额外检查。

## 五、可直接使用的 CI 示例

### npm

```bash
npm ci
npm run lint
npm test
npm run build
```

`npm ci` 要求存在 `package-lock.json`；如果它与 `package.json` 不一致会直接失败，并且不会改写两者。

### pnpm

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm lint
pnpm test
pnpm build
```

如果使用 pnpm workspace，根目录安装默认会处理工作区内的项目。缓存建议指向 pnpm store，并以 `pnpm-lock.yaml` 摘要作为缓存键的一部分。

### Yarn 1

```bash
yarn install --frozen-lockfile --non-interactive
yarn lint
yarn test
yarn build
```

### Yarn 2+

```bash
corepack enable
yarn install --immutable
yarn lint
yarn test
yarn build
```

如果采用 Yarn Zero-Installs 并接受外部贡献，还应参考 Yarn 官方建议，考虑增加 `--immutable-cache --check-cache`。

## 六、最终建议

如果是新建前端项目：

- 团队只选择一种包管理器；
- 提交对应 Lock 文件；
- 固定 Node.js 与包管理器版本；
- CI 使用冻结安装；
- 缓存下载内容而不是盲目缓存 `node_modules`；
- 构建一次并部署同一份不可变制品。

如果是 Maven 项目：

- 不要把“没有 Lock 文件”理解为“不需要可重复构建”；
- 固定 JDK、Maven、依赖和插件版本；
- 禁止动态版本和 Release 覆盖；
- 用 BOM、Enforcer 和可重复构建配置补齐约束。

无论前端还是 Java，生产 CI 的核心目标都一样：

> 同一份源码、同一套受控构建输入，应得到可验证、可追溯、可重复部署的制品。
