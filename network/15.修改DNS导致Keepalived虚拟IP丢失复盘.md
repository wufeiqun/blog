# 修改 DNS 后 Keepalived VIP 丢失：NetworkManager reapply 副作用复盘

## 背景

2026 年 9 月 14 日，北京测试 Kubernetes 集群的 24 台宿主机统一将 DNS 改为 `223.5.5.5`、`114.114.114.114`。操作范围只包括宿主机 DNS，不涉及 CoreDNS、Pod 或其他 Kubernetes 配置。

其中 `172.16.3.181` 使用 CentOS 7，主网卡为 `ens160`，NetworkManager 版本为 `1.18.8`，Keepalived 版本为 `1.3.5`。它有两类地址：

- 主 IP：`172.16.3.181/24`，由 NetworkManager 管理。
- VIP：`172.16.3.251/32`，由 Keepalived 动态添加到 `ens160`。

VIP 是网卡上的虚拟地址；“VIP 存在”和“业务进程监听端口”是两个不同检查项，不能用 DNS 53 端口的监听情况判断 VIP 是否存在。

修改前，宿主机 DNS 为 `172.16.2.94`、`223.5.5.5`。DNS 修改后，用户发现 VIP 消失；重启 Keepalived 服务后，VIP 恢复。

## 时间线与证据

以下时间均为北京时间，依据本次操作记录和服务器日志整理。

| 时间 | 事件与证据 |
|---|---|
| 10:35:24 | NetworkManager 记录 DNS 配置更新，随后记录 `device-reapply`，目标接口为 `ens160`。 |
| 修改后、服务重启前 | 只读查询网卡地址时能看到主 IP，但没有 `172.16.3.251`。 |
| 11:08:42—11:08:43 | 日志记录 Keepalived 停止并重新启动。 |
| 11:08:45 | Keepalived 进入 MASTER，执行 `setting protocol VIPs`，为 `.251` 发送 gratuitous ARP。 |
| 恢复后 | `ip addr` 中重新出现 `172.16.3.251/32`。 |

服务器启动时间仍为 2026 年 7 月 21 日，因此本次有证据支持的是 **Keepalived 服务重启**，不是整台服务器重启。

事发前的 Keepalived 日志没有发现主备切换记录；配置中的 `track_script` 引用已注释，未启用该 Nginx 健康检查。配置注释说明此处为单服务器使用 VIP。

## 原因分析

### 高可信原因：重应用网卡配置移除了外部 VIP

本次修改了 NetworkManager 连接中的 DNS 属性，然后执行以下命令使其生效：

```bash
nmcli device reapply ens160
```

这不是仅刷新 `/etc/resolv.conf` 的命令，而是重应用设备配置。Keepalived 添加的 VIP 不在 NetworkManager 的持久化地址配置中，属于外部添加的地址。

NetworkManager 官方文档说明，Reapply 可以撤销外部地址变更；从 1.42 起才支持 `preserve-external-ip` 标志，以保留外部添加的地址和路由。本机为 1.18.8，不能直接套用新版本的该保护能力。

结合命令时间、VIP 消失及 Keepalived 重启后恢复的事实，最符合现场的解释是：

```text
修改 DNS → reapply 网卡配置 → 外部 VIP 被移除
→ Keepalived 未自动补回 → 重启后进入 MASTER → 重新添加 VIP
```

**证据边界：没有捕获到事发时删除 VIP 的 netlink 事件，也未进行破坏性复现，因此这是高可信根因判断，不是对具体删除事件的直接证实。** 同样，Keepalived 当时为何没有补回 VIP，尚未通过源码或复现进一步确认。

### 操作与验收的疏漏

操作确实没有编辑主 IP、掩码、网关或 Keepalived 配置，但“未编辑 IP 字段”不能等同于“运行中的 IP 地址没有变化”。

原验收检查了 DNS、SSH、默认路由和 Kubernetes Node Ready 状态，没有比较完整网卡地址，也没有检查 VIP 业务入口。主 IP 和默认路由正常，并不能证明动态 VIP 未受影响。此前“没有影响 IP”的说明过于绝对，应以运行时地址检查结果为准。

## 本次恢复方式

用户重启 Keepalived 后，服务重新进入 MASTER 并添加 VIP，现场恢复已经通过日志和网卡地址确认。

对应恢复动作如下，仅记录本次处置，不应作为多节点主备环境的无条件操作模板：

```bash
systemctl restart keepalived
ip -4 addr show dev ens160
journalctl -u keepalived --since '5 minutes ago' --no-pager
```

在多节点环境中，恢复前应先确认主备角色及 VIP 当前归属，避免引发争抢。恢复后还应从实际访问端验证业务端口；仅看到 VIP 并不代表应用入口完全恢复。本次取证未记录完整业务入口验收结果。

本次分析没有再次修改服务器配置，也没有主动重启服务。

## 以后如何安全修改 DNS

### 这类 CentOS 7 主机：分别处理持久化与当前生效

该服务器的持久化配置位于：

```text
/etc/sysconfig/network-scripts/ifcfg-ens160
```

DNS 字段为：

```ini
DNS1=223.5.5.5
DNS2=114.114.114.114
```

对本机这类 NetworkManager 管理普通 `/etc/resolv.conf` 文件、同时运行 Keepalived 的环境，后续可采用以下流程：

1. 保存完整 IP、路由、DNS、Keepalived 状态及相关配置备份。
2. 通过 NetworkManager 修改连接的持久化 DNS 属性，但不执行设备重应用或连接重新激活。
3. 仅替换 `/etc/resolv.conf` 中的 `nameserver` 项，使当前解析使用新 DNS；保留原有 `search`、`options`、文件权限和安全上下文。
4. 回读持久化配置及当前 DNS，并比较修改前后的完整地址集合，确认 VIP 仍在。

只改 `/etc/resolv.conf` 可能在后续网络事件中被覆盖，所以持久化配置也要同步。若直接编辑 ifcfg 文件，应区分“重新读取连接配置”和“重应用设备配置”，不要为了修改 DNS 顺手执行 `reapply`、连接 down/up 或重启网络。

上述流程是后续建议，**本次未重新执行**。Ubuntu 使用 systemd-resolved 时，`/etc/resolv.conf` 可能是指向本地 stub 的软链接，不能照搬直接写普通文件的做法；应按实际管理方式处理。

### 变更前后必须检查动态网络状态

- 识别 Keepalived、其他 VIP 管理器以及动态添加的 IP、路由。
- 保存并比较 `ip -4 addr`、`ip -6 addr`、路由以及 VIP 所属网卡。
- DNS 修改后检查持久化值、运行时值、解析结果，同时核验 VIP 和实际业务入口。
- 批量变更的试点必须覆盖带 VIP 的节点，不能只按操作系统选样本。
- 一旦发现 VIP 消失，应停止后续变更，先按现有主备关系恢复；不要在在线服务器上重复执行有风险的命令做复现。

需要进一步证明机制时，应在隔离环境使用相同 NetworkManager 版本，通过临时地址和 `ip monitor address` 观察 Reapply 行为。
